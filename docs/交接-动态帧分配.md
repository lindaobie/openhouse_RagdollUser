## 二、接下来的任务：动态帧分配

### 要解决的问题

现在固件严格平均轮转：

```c
/* multi.c: The k-th of them sweeps in the revolutions rev % count == k */
return (rev % count) == k;
```

四台在线 → 每台每 4 转扫一次 → 每轴 15 Hz，**不管设备看不看得见它**。

浪费场景：

```
tracker A 只看得到 基站 1、2
tracker B 只看得到 基站 3、4
→ 1、2 扫的时候 B 收不到，3、4 扫的时候 A 收不到，两边各有一半时间白等
```

### 四段原理

**1. 信息（驱动有，基站没有）**

`DeviceTracker::lastFrame_` 是 `map<baseSerial, lastSweepTime>`，天然就是"每台设备能看见哪些基站"。

基站侧完全空白——tracker 不发光，基站看不见设备。

**2. 决策（驱动算）**

max-min 公平的启发式：

```
w_j = Σ(i : j ∈ S_i) 1/|S_i|     然后归一化
```

每台设备把一票均分给它看得见的基站。服务设备多的基站权重自然高。

**3. 下发（主站 USB → OOTX 广播）**

- 驱动通过 USB CDC 把权重写给主站
- 主站把权重/轮转表编进 OOTX 帧 payload
- 主站用 `ootx_build()` 重建帧，`announced_at = ootx_frames_sent()` 等整帧发完才生效
- 从站解码后跟随

**协议扩展要小心**：帧是 `u16 长度 + payload + pad + crc32`，加字段会让老固件 CRC 拒绝整帧——这是**安全失败**（老固件停在最后一版已知配置，不会乱扫）。

**4. 执行（固件换一块地砖）**

```c
// 原来
return (rev % count) == k;
// 改成
return schedule[rev % schedule_len] == MC->slot;
```

`schedule[]` 是 16 项的轮转表。**上层时序（超帧、guard、相位对齐）一个字不动。**

### 时间尺度

权重更新 1 秒级，OOTX 广播秒级，从站下一个超帧生效。跟上"人走动、基站被挡"这种慢变化，跟不上快速翻转。

## 三、硬件条件（用户已确认具备）

- **同步线**（3.5 mm，基站之间）
- **超长 micro-USB**（电脑 ↔ 单台基站）

两条路线可以并行验证：

**路线 A：无线从站 + USB 到主站**
```
电脑 ──USB──> 主站 ──OOTX 光──> 从站 ×3
```

**路线 B：同步线**
```
电脑 ──USB──> 主站 ──3.5mm──> 从站（串起来）
```

同步线不传数据，只传脉冲宽度（现在编码一个 skip flag）。它的价值是**相位更稳、抗遮挡**，不是传调度。

## 四、动手前必须先验证的三件事

1. **主站长期挂 USB CDC 时能否正常发射**——lhbs 的 USB CDC 是运行时控制台，但没在基站端长期占用过，可能和发射冲突。这是路线 A 的生死线。
2. **同步线的基线数据**——4 台插线走 A/b/c vs 现在无线 multi，追踪质量差多少。这个数据决定动态调度值不值得做。
3. **OOTX 帧加字段后老固件的反应**——确认是拒绝整帧（安全），不是解析出垃圾。

### 现在的调度是怎么走的

```
主站 multi_task()（每 100ms）
  → 统计 seen_ms[]：最近 500ms 内看到过闪光的从站
  → 掩码 c = 1 | 那些从站
  → 稳定 1 秒后 ootx_build()，把掩码写进 OOTX byte 33
  → announced_at 等到整帧发完，set_mask(announced)

从站
  → 解 OOTX 帧 → pending → 下一个超帧 set_mask()
  → multi_sweeps_in(rev): (rev % count) == k
  → 有 guard（4 个超帧）保证切换安全
```
